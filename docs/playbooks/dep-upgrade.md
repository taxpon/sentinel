```text
## Overview

An advisory against a pinned dependency, and the call-site changes the upgrade
forces. Changing the version number is the smallest part of this work and never
the part that is being judged.

## Procedure

1. Establish why the pin is where it is, before choosing a target version.
   - A pin that sits behind a published fix is usually held there deliberately.
     The reason is a comment on the pin itself, a cap in pyproject.toml, or a
     transitive dependency that still calls an API the new major removed.
   - Finding that constraint is the task; the bump is what happens afterwards.

2. Confirm for yourself which release actually carries the fix.
   - An advisory that records only a last-affected version does not tell you
     which release fixed it, and the issue may hand you an inferred answer and
     say that it is inferred.

3. Find the second-order records that name the package by major version.
   - They live in sections a version bump would not otherwise touch. The
     liccheck allowlist under [tool.liccheck.authorized_packages] is one of them,
     and a diff that misses it fails the licence check for a reason that has
     nothing to do with the advisory.

4. On the frontend, derive the scope from import sites rather than from the
   audit's package list.
   - Families such as deck.gl and luma.gl require matching majors across their
     subpackages, so remediating one forces all of them.
   - The code that breaks lives in the plugins that import the family, not in
     the flagged package, which may have no import site anywhere in the tree.

5. Adapt the call sites the upgrade forces, and test those paths.
   - They are what creates the evidence: the key-loading and transport paths for
     an SSH library, the plugin's own render and layer tests for a frontend
     family bump. Those are the assertions that would have caught a two-major
     jump going wrong.

6. Regenerate lockfiles and compiled requirements with the project's own
   tooling, and commit the result.

7. Run the frontend type-check locally before you push.
   - The type-checking-frontend hook is skipped in this CI, so it runs nowhere
     on the pull request. A major bump is precisely the change that breaks types
     without breaking a test.

## Specifications

1. The version you land on is the one that carries the fix, confirmed against
   the advisory rather than inferred from a last-affected version.
2. Every second-order record naming the old major moved with the pin, and the
   lockfile or compiled requirements were regenerated by the project's tooling
   rather than edited.
3. For a frontend family, every subpackage sharing the major moved together, and
   the plugins that import them still build and pass their own tests.
4. structured_output.tests.added names assertions that exercise a path the
   upgrade actually changed. A version constraint is not a test, and the field
   is not allowed to be empty for this class.
5. root_cause states the constraint that held the dependency on the vulnerable
   version, and what you did about that constraint.
6. The pull request claims only that the upgrade did not break Superset. It does
   not claim the vulnerability was demonstrated closed.

## Advice & Pointers

What CI will tell you, and what it cannot.

Python: changing pyproject.toml, setup.py or requirements/*.txt runs the whole
tests/unit_tests suite. That is the broadest signal any remediation class gets
here, and for a multi-major jump it is the best evidence available. It is worth
the wall clock.

Frontend: superset-frontend/package.json and superset-frontend/package-lock.json
map to no test target at all. A diff that changes only manifests and the lockfile
runs jest on nothing, and the check suite still concludes green with a warning
that no test target could be derived. The jest signal exists only for packages
whose source files you actually edited. Bump and stop, and the green tick means
nothing.

Neither signal exercises the vulnerable code. Nothing in Superset's test suite
feeds a malformed image to an image parser or an SHA-1 signature to an SSH
transport. What this CI can prove is that the upgrade did not break Superset.
Write that in the pull request in those words.

If the upgrade genuinely required no source change, the honest report is that the
evidence is a regenerated lockfile and a suite that still passes. Say so in
root_cause and set confidence to match.

root_cause: "The pin was capped below the fixed major because a transitive
dependency still imports a key type that major removed" is a root cause.
"Upgraded from 3.5.1 to 5.0.0" is a changelog entry.

Budget: 10 ACUs, the smallest of the four playbooks, and dependency resolution is
where it disappears fastest. If the resolver will not converge, or the transitive
blocker has no release that clears it, report outcome "blocked" naming the
specific constraint and what would have to change. For this class that is a
complete answer, not a failure.

## Forbidden actions

- Hand-editing a lockfile or a compiled requirements file. It is the most common
  way this class produces a build nobody can reproduce.
- Treating the audit's package list as the scope of a frontend family bump.
- Leaving structured_output.tests.added empty on the grounds that a version
  constraint is the whole change. A version constraint is not a test.
- Inventing an assertion that exercises nothing the upgrade touched, so that the
  field is non-empty.
- Raising or removing a cap without first establishing what it was holding back.
- Writing the pull request as though the vulnerability itself had been
  demonstrated closed.
```
